Share a Model

Before every submission, read this live page with atlantis_gallery_requirements (standalone MCP: read_gallery_requirements). Use the returned requirements_digest for preparation and publication. If these requirements change, read them again and review the updated plan.

Update your existing Atlantis client. When a modeling task is ready, ask your Atlantis assistant to share it, then confirm the files you want to make public.

Prepare your GitHub account

The current Atlantis client includes the Gallery publisher. Update the existing installation using the client update guide, then reload Codex once to discover the new tools. Install Git for Windows with Git Credential Manager and sign in to your own GitHub account:

$galleryUser = Read-Host 'Your GitHub username'
git credential-manager github login --username $galleryUser

For multiple GitHub accounts, set ATLANTIS_GALLERY_GITHUB_USER to the intended username in your Atlantis MCP environment. Never paste a token into a chat.

Share from an Atlantis modeling chat

Share this asset to Atlantis Gallery. Prepare a submission from the final model, textures, motion files, modeling code, and the work order I approve. Convert all user-visible interaction text in the upload package to English and verify the controls in the browser preview. Keep my creator name and control mappings. Show me every public file and its storage destination before publishing.

atlantis_gallery_prepare creates a local package and lists its files, archive members, checksums and destinations. After you approve that exact public plan, atlantis_gallery_publish uses your GitHub account to publish it. Changed files require a new plan and approval.

  • Your public atlantis-<slug> repository hosts preview models, textures and browser motion logic through GitHub Pages.
  • GitHub Releases in that repository host exactly three current downloads: model assets, combined controls, and editable modeling source. An approved work-order JSON is included inside the source archive.
  • The main Gallery receives only a catalog entry and a thumbnail of at most 1 MiB. Your work page keeps your creator name, downloads, interactive preview and social links.

The publisher verifies Pages access, browser CORS and file hashes before submitting the Gallery entry. Pages may need time to deploy; retry the same approved digest to resume without duplicate downloads. Contributors receive a pull request; work appears after maintainers merge it and Gallery Pages deploys. The Gallery owner publishes directly.

Preview files must each be smaller than 100 MiB, total at most 900 MiB. Each Release download must be smaller than 2 GiB. Optimize oversized previews before publishing.

The WebGPU viewer's Share To Atlantis Gallery button opens this guide. Publication still requires your reviewed file plan.

Publish three packages and keep updates together

  1. model.zip: final USD/GLB models, referenced layers, textures, materials and other model assets. Preserve the export's relative paths.
  2. controls.zip: all operation code and dependencies, including simplified game logic and native real-physics adapters when supplied, configuration, launchers, runtime manifests and assembly instructions. Keep the two solvers independent. Do not advertise an adapter that is absent.
  3. modeling-code.zip: editable modeling code for every part, rebuild inputs and instructions, plus the optional work order approved for public sharing.

Do not add separate simplified-motion, real-physics or work-order download buttons. On an update, rebuild the affected packages and replace the work page's current links. Preserve the work ID, author and social links; old release archives may remain as history.

Extract the model and controls packages into the same dedicated directory. Extract modeling source separately. Include ASSEMBLE_ISAAC.md and ASSEMBLE_GAME_ENGINE.md in controls; the publisher adds baseline instructions when they are not explicitly supplied. Provide asset-specific commands and isaac-runtimes.json for advertised Isaac adapters.

Both Gallery assembly actions must use all three current package links, explain this extraction layout, select the supplied runtime and activate only one controller per instance. Isaac PhysX runs in Isaac Sim. A game-engine work order must adapt host bindings or use that engine's native solver.

Use modelFiles for assets, motionFiles and controlFiles for all operation code/configuration, and sourceFiles for editable modeling source. Browser code in previewFiles is also included in controls. The generated package instructions are listed in the reviewed public plan. Static assets still use these three roles; never claim nonexistent behavior.

Existing standalone Gallery MCP installations

They remain supported. Run git pull --ff-only inside the existing AtlantisGallery checkout and restart that MCP. Its tools remain prepare_gallery_upload and publish_gallery_asset. New Atlantis users do not need a second MCP or Python environment.

Operate vehicles directly on the Gallery work page

Declare operableVehicle in every new submission. Set it to true for every vehicle that has operating logic, including bicycles. Visitors must be able to enter operating mode, control the vehicle and return to model inspection on its Gallery work page.

Use a supported native Gallery vehicle controller or set vehicleEntry to the relative path of a browser-ready HTML controller. Include its scripts, styles, models and other dependencies in previewFiles. Keep camera and keyboard controls usable inside the embedded view. A video, an external launch link or a downloadable engine project alone does not fulfill this requirement.

Before requesting approval, test the submitted build inside the Gallery work-page frame. Enter operating mode, use the controls supplied by the vehicle (for example pedal, steer and brake), confirm visible motion, and return to inspection. Record the actions and observed results in the review.

Simplified ground-vehicle driving defaults to acceleration, coasting, braking and parking hold, stop-before-reverse, contact-based traction, bounded per-wheel spring/damper suspension, terrain pitch/roll, mild hard-brake nose dip that settles, no airborne traction, and landing response. Bind actual wheels, arms and tracks correctly. Apply these features to the actual construction: reverse requires powered reverse, differential steering requires a suitable vehicle, and a hardtail bicycle retains its rigid rear end and front fork without an invented reverse gear, rear suspension or tracks. Use fixed substeps, safe input release and a pure Python core tested in Pyodide. Test start, coast, brake and settling, reverse where supported, steering, slope and one-sided bumps, airborne/landing and 30/60/144 Hz input. Native real physics uses separate solver validation and must not receive duplicate simplified suspension or body integration.

Concurrent submissions

Each work has its own _data/works/<asset-id>.json and models/<asset-id>/ directory. Pages builds the combined index after merge. Leave catalog.json to existing records. Two different work IDs can merge in either order. For a conflicting older PR, move its new record into its own file and restore the main branch’s catalog before merging. Check authorship and content whenever the same ID is claimed twice.

Use English for model interactions before packaging

Before preparing an upload, convert all user-visible interaction text in the Gallery copy of the asset to English. This requirement applies to the model and its controls; your documentation and private conversation can remain in their original language.

  • Translate button captions, menus, switches, field labels, control hints, keyboard and mouse instructions, tooltips, status text, and messages shown by the motion or control scripts.
  • Check interaction.json, Python and browser control scripts, and any visible operating text on the model. Vehicle and viewport mode controls must also use English, for example Drive Mode (F1), Viewport Mode (Esc), and WASD: Drive · Mouse: Look and Aim.
  • Keep the creator's chosen display name, prim paths, joint and event IDs, binding keys, keyboard mappings, and motion behavior. Change display text without renaming machine identifiers.
  • Operate the actual browser preview before preparing the upload. Verify the English text, buttons, keyboard and mouse controls, and linked part movement. Resolve missing browser adapters before presenting the package as ready.

Describe the export

The assistant writes submission.json next to the export. All paths are relative to that file. Supply an English title, your display name, a rendered thumbnail, and the files you want to share.

{
  "schema": "atlantis-gallery-submission/1",
  "slug": "hinged-cabinet",
  "operableVehicle": false,
  "title": "Hinged Cabinet",
  "creator": "Your Display Name",
  "model": "cabinet.usd",
  "thumbnail": "preview.webp",
  "previewFiles": ["textures/oak.png"],
  "modelFiles": ["cabinet-detail.usd"],
  "interaction": "interaction.json",
  "motionFiles": ["motion/cabinet.py"],
  "controlFiles": ["ASSEMBLE_ISAAC.md", "ASSEMBLE_GAME_ENGINE.md"],
  "sourceFiles": ["modeling/build_cabinet.py"],
  "workOrder": "work-order.json"
}
  • List dependencies required by the web preview in previewFiles, with the paths the model expects. Use a browser-ready USD or GLB export.
  • Use modelFiles for additional model assets and USD layers. Use motionFiles and controlFiles for operation scripts, configuration and runtime dependencies in the combined controls download.
  • List the final modeling code for every part and its required data in sourceFiles.
  • Include workOrder only if you approve the complete JSON for public download. Review it for private information before sharing.
  • Provide interaction for browser controls. It maps part paths to joints, buttons, and emit events. The existing microwave uses the shared Python profile. The Tiger II profile loads its pure Python module and motion configuration from explicitly listed preview dependencies. Other new Python profiles require a Gallery adapter.
